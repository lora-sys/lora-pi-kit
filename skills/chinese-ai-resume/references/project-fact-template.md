# 项目事实清单模板

在写任何项目条目之前，先为每个候选项目完成此表。没有证据的结论不写进简历。把“将来准备做”“本地模拟过”“设计里有”与“仓库中已经实现并可复现”分开。

| 字段 | 要写的内容 | 可接受证据 |
|---|---|---|
| 项目定位 | 它为谁解决什么具体问题。不要用“平台”“生态”等空词代替场景。 | README 的问题描述、Demo、公开页面。 |
| 本人角色 | 本人做了哪些模块或决定。区分个人实现与团队成果。 | Git 提交、代码目录、Issue、技术文档。 |
| 架构边界 | 服务、Agent、数据、界面分别负责什么。 | 目录结构、接口定义、架构图、部署文件。 |
| 关键决策 | 选择这种数据流、状态机、锁、审批或降级方案的原因。 | 代码、测试、设计说明。 |
| 难点与修复 | 出现过什么真实错误、风险或约束，后来怎样处理。 | Bug 修复提交、回归测试、Issue。 |
| 质量证据 | 测试数量、覆盖的场景、公开演示、可复现命令。写测试类型与结果，避免无出处的性能数字。 | CI、测试输出、Playwright 报告、README。 |
| 真实边界 | 未完成、仅 Mock、仅单机、外部运行时受阻或待补测的部分。 | TODO、Issue、实现状态。 |
| 公开链接 | 仓库、Demo、博客或视频。 | 访问时返回可用状态。 |

## 项目写作输入模板

```text
项目名称：
链接：
项目介绍：用 2 至 3 句写清场景、问题和当前成果。

1. 架构或数据流：我如何拆分模块，解决什么具体混乱或风险。
2. 关键决策：我为什么在这里用某个机制，而不是只堆工具名。
3. 难点：我处理过什么失败、并发、重复、超时、证据不足或协作问题。
4. 质量：我用哪些测试或可复现步骤验证了什么。
5. 边界：哪些能力仍未完成，或者只在何种范围下成立。
```

> 一条项目工作只陈述一个主张。能回到仓库、测试或演示验证的句子才值得保留。
