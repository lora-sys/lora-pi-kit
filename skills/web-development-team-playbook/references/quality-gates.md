# Web 项目质量门禁

在每轮实现、修复、交付、性能优化、发布准备或部署前读取本文件。所有结论必须基于当前运行产物、命令输出或可复核截图；不得用代码阅读替代运行验证，也不得把未做检查写成通过。

## 执行顺序

优先使用仓库现有脚本和 Vite+ 当前兼容的工作流。开始前检查 `package.json`、锁文件、README、CI 配置和项目约定；不要捏造通用命令或为检查而引入无必要依赖。

1. **静态正确性：** 运行项目既有的格式检查、类型检查、单元/集成测试和生产构建。记录命令及其真实结果。
2. **功能和交互：** 验证用户主路径以及成功、加载、空、错误、拒绝、取消和重试路径。对每项改动列出可观察的预期与实际结果。
3. **响应式：** 在真实窄屏和宽屏视口检查布局、导航、输入、表格、媒体、触控目标和内容溢出；不要只查看开发者工具中的单一宽度。
4. **视觉证据：** 对用户可见变更，在可行时制作变更前后截图。动效、时序、拖放或多步流程为重点时，使用短录屏或等效的可重复交互证据。
5. **性能：** 检查首屏、交互、图像/字体、代码分包、大表格/列表和 Canvas/3D 场景的瓶颈。将发现的问题与真实用户影响关联；不要只报抽象分数。
6. **SEO：** 检查与项目性质相适配的标题、描述、语言、规范链接、索引控制、语义结构、可抓取的主要内容、站点地图/机器人规则和社交元数据。
7. **无障碍：** 检查键盘路径、可见焦点、名称/角色/值、对比度、标题层级、表单标签、错误提示、模态焦点管理、动态内容公告和减少动态效果。
8. **隔离对抗审查：** 按 `review-protocol.md` 进行。真实问题修复后，重新执行受影响的门禁。

## 证据矩阵

| 门禁 | 每次要求 | 合格证据 | 常见失败 |
|---|---|---|---|
| 类型/构建/测试 | 必做 | 现有脚本的成功输出，或失败的明确说明与未能修复原因 | 只说“应能构建”、忽略类型错误、跳过已有测试。 |
| 成功与错误路径 | 必做 | 逐条运行结果、截图、日志或测试 | 只测试理想路径；失败后仍显示成功。 |
| 移动端与响应式 | 必做 | 窄屏与宽屏的实际检查证据 | 桌面布局简单缩放；导航/表格溢出。 |
| UI 截图/录屏 | 用户可见变更时必做（可行时） | 前后截图；动效/拖放等以录屏或交互证据 | 只给代码片段；用静图证明时序。 |
| 性能 | 必做 | 对受影响路径的测量或可观察检查，及优化/不适用理由 | 盲目追逐单一评分；漏掉图片、长列表或 3D 负担。 |
| SEO | 必做，或明确标注不适用 | 元数据与可抓取性检查；若不适用，记录任务性质与原因 | 对内网/原型静默跳过；公共页没有语义标题。 |
| 无障碍 | 必做 | 键盘、焦点、语义、对比度和动态状态检查 | 只检查颜色；遗漏焦点、标签、错误和模态。 |
| 对抗审查 | 必做 | 独立审查摘要、问题核验与修复复验 | 审查者获知需求/计划；为自动评论修改正确代码。 |

## 按项目性质适配

所有门禁都要评估，不能静默跳过。纯内网后台、一次性原型、没有公开路由的工具可以使 SEO 的部分检查不适用，但必须在交付中说明：它为何不被公开索引、哪些元数据/语义仍然适用，以及未做的具体项目。对公共内容站，SEO 和性能必须根据实际公开页面逐一检查。

对于数据密集应用，补充检查分页、排序、筛选、空数据、权限拒绝、网络中断、大量数据、低性能设备和键盘表格操作。对于 3D/Canvas，补充检查资源加载、WebGL 不支持、低性能降级、暂停/恢复、触摸、键盘和可访问替代内容。对于表单，补充检查验证、服务端拒绝、重复提交、网络重试、密码管理器/自动填充及错误恢复。

## 交付摘要模板

交付时提供简洁事实摘要：

| 项目 | 应写明的事实 |
|---|---|
| 已完成 | 用户可见行为和涉及的主要文件/区域。 |
| 计划与范围 | 已实现范围、明确未做的范围与原因。 |
| 验证 | 实际运行过的命令、测试路径、视口、截图/录屏和核心结果。 |
| 审查 | 已核验的对抗审查发现、实际修复和误报反证。 |
| 限制 | 未完成、不可验证、外部依赖或需要用户后续决定的事项。 |
| 发布 | 仅陈述准备状态；真实部署操作必须等待本次明确确认。 |

> “检查未发现问题”不是证据；应说明检查了什么、在什么环境中、得到什么实际结果。
