# Web 技术选型与工具链

在新建项目、评估迁移、增加重大依赖或升级框架时读取本文件。不要使用这一文件中的文字代替当前官方文档：每次实际决策前都要打开对应官网，核对当前稳定版本、迁移要求、运行时支持和项目兼容性。

## 决策顺序

先判断是否应该**不改变**当前项目技术栈。已有项目的现有框架、路由、查询层、表格、测试、构建系统和部署方式若能满足需求，应优先延续。新框架必须解决一个具体、当前的问题；不能仅因偏好或版本新而替换成熟代码。

新项目或确需选型时，依次判断渲染与 SEO、全栈边界、客户端交互复杂度、团队既有能力、Vite+ 可用性、部署约束和 3D/Canvas 需求。记录至少一条真实选择理由和一条不选主要替代方案的原因。

| 条件 | 默认选择 | 需要确认的关键问题 |
|---|---|---|
| 公共内容、搜索可见性、服务端渲染、复杂缓存或服务端组件 | Next.js | 需要哪些渲染策略？数据缓存与失效如何建模？部署环境如何支持？ |
| 交互型 SPA、营销页、纯前端内部工具或嵌入式页面 | Vite | 是否确实不需要服务端渲染、Server Functions 或 SEO？ |
| 全栈 React、Server Functions、端到端类型安全和深度 TanStack 工作流 | TanStack Start | 服务端函数、路由数据加载与运行时是否匹配当前部署？ |
| 复杂路由 | TanStack Router | 是否已有成熟路由方案？类型安全和数据加载需求是否值得迁移？ |
| 远程数据、缓存、失效、分页、乐观更新 | TanStack Query | 查询键、失效和错误/重试策略是否显式定义？ |
| 大表格、排序、筛选、分页、列配置 | TanStack Table | 大数据量是否需虚拟化、服务端过滤或无障碍表格设计？ |
| 3D、空间交互、WebGL 场景 | React Three Fiber | 性能预算、触屏/低配降级、加载失败和无障碍替代是什么？ |
| 并发、重试、资源生命周期、领域错误或未知数据验证 | Effect 生态 | 是否让 Effect 在边界层与领域层发挥作用，而非包装简单 UI 状态？ |

## Vite+（`vp`）优先规则

优先将 Vite+ 作为适用项目的统一工具链入口。实际开始前，按以下顺序处理：

1. 阅读 [Vite+ 官方入门文档](https://viteplus.dev/guide/) 和其面向模型的完整指引（如官网提供）。
2. 检查当前仓库的运行时、包管理器、锁文件、CI 和脚手架是否兼容；不得覆盖既有设置以“强行统一”。
3. 使用当前官方推荐方式确认 `vp` 的安装、开发、检查、测试、构建和格式化工作流。
4. 对 Next.js 或其他非 Vite 原生项目，先验证当前 Vite+ 兼容性；不兼容时记录理由并保留项目既有工具。
5. 不在团队技能中写死 `vp` 子命令、配置键、插件版本或兼容性矩阵；它们随工具演进，应以官网与项目实际版本为准。

> Vite+ 是优先工具链，不是为了追求一致性而破坏已有稳定工程的迁移指令。

## Next.js 选择守则

使用 [Next.js 官方文档](https://nextjs.org/docs)确认当前 App Router、缓存、数据获取、路由处理和部署约束。为每个数据边界明确选择服务端、客户端或混合模式。不要把浏览器专属 API、事件状态或长生命周期交互意外放进服务端组件。将机密和服务端权限留在服务端边界。

## Vite 选择守则

使用 [Vite 官方文档](https://vite.dev/guide/)确认当前初始化、环境变量、生产构建、插件和静态资源规则。保持 SPA 路由与生产静态托管的回退策略一致。不要把大媒体、机密或后端业务逻辑塞入纯前端构建产物。

## TanStack 选择守则

使用 [TanStack 官方文档](https://tanstack.com/)确认框架适配、当前 API 和运行时约束。将路由、查询、表格状态建模为显式数据流，而不是由组件渲染顺序隐式推断。

- **Router：** 明确路由参数、搜索参数、加载状态、错误边界、权限边界和返回路径。
- **Query：** 设计稳定的查询键、失效策略、错误策略、分页策略和乐观更新回滚。不要在渲染期创建不稳定查询输入。
- **Table：** 区分客户端与服务端的排序、筛选、分页；为窄屏、键盘和屏幕阅读器设计可操作替代。
- **Start：** 在使用 Server Functions、服务端加载或端到端类型时，确认部署与运行时支持；勿让服务器实现细节泄漏至通用客户端状态。

## Effect 默认采用规则

Effect 是 TypeScript Web 项目的默认评估对象，尤其适用于复杂异步流程、并发、资源生命周期、可恢复错误、领域错误和不可信输入。开始使用前阅读 [Effect 官方文档](https://effect.website/docs/)。

将 Effect 放在真正受益的边界：服务层、数据获取与转换、校验、工作流和复杂状态机。简单的本地 UI 控制（例如单一受控输入或临时 hover）不必机械包裹。保持 Effect 错误模型可映射到真实用户反馈和日志；不要因抽象而掩盖底层失败状态。

## React Three Fiber 选择守则

使用 [React Three Fiber 官方文档](https://r3f.docs.pmnd.rs/)确认当前 API。为每个 3D 功能事先定义首屏资源预算、加载/错误/低性能路径、键盘与触屏输入、降级体验和静态替代内容。不得让 3D 场景阻塞普通内容、基本交互或辅助技术访问。

## 输出选型结论

在计划中用一小段写清：当前/拟用框架，Vite+ 的适用与否，路由/数据/表格/3D/Effect 的决定，当前官方文档核验状态，以及不选择主要替代方案的原因。不要输出只含框架名的“选型”。
